**Decisão: Azure AI Search + Azure OpenAI nativo (Buy)**

Os quatro fatores que determinaram a escolha, com os principais contra-argumentos:

**A favor do Buy — onde o build perde:**

| Fator | Por que o build perde |
|---|---|
| **Prazo** | O conector com SharePoint via Microsoft Graph é 2–4 semanas de engenharia; o Indexer nativo é configuração. Em 3 meses, isso é 17–33% do prazo. |
| **Qualidade de OCR** | Tesseract erra silenciosamente em tabelas complexas e layouts mistos. Erros de extração contaminam o índice sem que o pipeline perceba — violação direta do requisito "nunca inventar informações". |
| **Consistência** | A ADR-0002 já define o Azure AI Search Semantic Ranker como componente de reclassificação. Build exigiria substituí-lo por um cross-encoder open-source, contradizendo uma decisão anterior. |
| **TCO real** | O build tem $50/mês de infra, mas $18k–30k de desenvolvimento de conector. O buy tem $270/mês de infra e $1,5k de configuração. O break-even favorece o buy no horizonte de 2 anos. |

**Onde o build tem argumentos legítimos (devil's advocate):**

- O custo operacional mensal do Azure AI Search é ~5x maior — se o volume crescer, essa diferença importa.
- A vantagem do conector nativo cobre apenas o SharePoint (~65% dos documentos); Confluence e planilhas exigem desenvolvimento customizado em ambos os casos.
- Lock-in real: a camada de recuperação fica acoplada ao Azure AI Search sem possibilidade de migração gradual.
- Flexibilidade de chunking para PDFs com tabelas não-padrão pode exigir pré-processamento fora do Indexer, parcialmente anulando a vantagem de integração.
